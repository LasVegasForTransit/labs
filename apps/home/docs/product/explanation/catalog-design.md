# Catalog design

Labs home presents public-interest work as civic evidence, not as a software showcase. Residents
need to understand what each project does and what it says about Southern Nevada. Policymakers,
advocates, journalists, and researchers need enough context to judge its relevance. Contributors
remain welcome without becoming the primary audience.

The catalog looks made by people who work with data and software, but it does not borrow the visual
language of a developer portal. Technical character comes from transparent methods, precise
metadata, and visible stewardship rather than terminal motifs, ornamental code, or invented system
readouts.

## Information hierarchy

The opening identifies LVBT Labs with one plain description. A distinct editorial band then explains
what the program publishes, how projects differ in maturity, and why the work remains open to public
scrutiny. This context answers what Labs is without turning the page into a marketing introduction.
The catalog follows directly.

Each entry begins with the project title and a concrete description of what someone can see or do.
The primary action and a visual of the actual work follow: a map, chart, publication detail,
interface state, photograph, or source document. A screenshot earns its space only when its contents
remain understandable at the displayed size.

Project metadata answers practical questions without competing with the main narrative:

- What kind of work is this?
- When was it published or last updated?
- What stage is it in?
- Where does its source code live?

The catalog grows into distinct groups as projects reach different lifecycle stages. Active work
remains prominent. Recently updated, graduated, deprecated, and archived work appears under plain
labels only when records exist in those groups. Empty sections and premature filtering controls do
not appear.

## Visual language

LVBT's paper, ink, ember, coral, and stone palette provides the common foundation. Project-owned
maps, diagrams, documents, and interface captures supply most of the page's visual variation. The
catalog does not manufacture variety with gradients, glowing borders, floating shapes, or a grid of
decorative cards.

Public Sans carries an editorial hierarchy. Large type is reserved for the page identity and project
titles. Captions, metadata, and source notes use compact type with comfortable line height.
Monospace is limited to values that are inherently machine-readable, such as a release identifier,
and never becomes the site's personality.

Rules, alignment, spacing, and shifts in scale establish structure. Containers appear when they
express a real boundary, not as a default treatment for every section. Project previews align with
their explanatory copy as editorial spreads on wide screens and as a deliberate reading sequence on
narrow screens.

Dark mode preserves the same hierarchy and does not turn the page into an uninterrupted charcoal
dashboard. Raised surfaces, borders, and imagery remain distinguishable without adding luminous
effects.

## Technical register

Technical details help visitors understand provenance, currency, and limitations. Useful details
include update dates, lifecycle state, maintainers, data sources, methodology, documentation, source
code, and short statements about known constraints. They use ordinary labels and remain close to the
project they describe.

Repository statistics, build badges, dependency versions, fake diagnostics, code fragments, and
GitHub activity counts do not explain the civic value of a project. They stay out of the public
catalog. Internal implementation details belong in project documentation unless they materially
change how a visitor should interpret the work.

## Footer

The footer adapts the main Las Vegas for Better Transit footer rather than introducing a separate
Labs convention. The LVBT wordmark, organization directory, involvement directory, mission
statement, ember stripe, and utility row make the relationship between the two sites visible.
Labs-specific contribution and source links sit in the utility row without repeating the project
catalog.

A project names a specific need only when maintainers are actively seeking help. Contributor
language never interrupts the primary path into an experiment or assumes that visitors understand
GitHub.

## Interaction and responsive behavior

The entire page remains usable with a keyboard, and lifecycle information never relies on color.
Links describe their destination. Focus treatment uses the shared brand foundation, motion respects
the visitor's reduced-motion preference, and decorative media does not enter the accessibility tree.

Mobile layouts preserve the project title, meaningful visual detail, and primary action. They do not
shrink a desktop screenshot until its labels become illegible. A project can provide a mobile crop
or alternate preview when the wide composition does not survive a narrow viewport.

Layout changes do not change the content order. Metadata follows the project explanation, and
secondary contribution links remain secondary at every viewport size.
